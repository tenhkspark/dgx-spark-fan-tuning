# 4ノードDGX Sparkクラスタのファンカーブ記録

4ノードのDGX Spark（GB10）クラスタでファンが実際にどう振る舞ったか、行き着いたカーブ、
そしてファンを黙って止めてしまうファームウェアの罠についての記録です。私たちが使っている
配信レシピ（`christopherowen/spark-ds41f`）はファンの設定を同梱していません。ファン制御は
上流では別プロジェクト（`christopherowen/dgx-spark-fan-control`）なので、その数値をここに置きます。

このリポジトリは**1枚のパッチと記録**です。フォークではありません。

- `patch/0001-performance-curve.patch` — 上流のユーザーランド制御器の`PERFORMANCE_CURVE`を
  差し替えるだけ。他は触りません。自分のチェックアウトに当ててください。
- `docs/` — カーブ、その背後にある実測、避けるべきファームウェア版。
- `scripts/` — 読み取り専用のスナップショットと、どのホストにも置ける熱監視。
- `deploy/` — モジュールの自動ロード設定とsystemdユニット（上流のベンチが要求する別名付き）。

```
NVIDIAファーム（EC） ──►  dgx_ec_fan_control カーネルモジュール
                                  │  cooling device: 加算的な「ファン床」state 0..12
                                  ▼
                       dgx-fan-control デーモン（userland・上流＋このパッチ）
                                  │  2秒ごと: 平滑化した最高温ゾーン ──► state
                                  ▼
                     ファン: state 1 ≒ 2,700 RPM … state 12 = 9,000 / 13,500 RPM
```

## まず知るべき故障モード

私たちの4台では、カーネルモジュールをロードしたまま**デーモンを動かさない**と、両方のファンが
**0 RPM**になりました。SoCの熱ゾーンは**96 °C**に達し、プラットフォームはGPUを**611 MHz**に
固定しました。`nvidia-smi`は利用率96%・8〜11 Wを報告し続け、`HW Thermal Slowdown`は出ません。
制限がGPUダイ側ではなくSoC側から来るためです。2台がこの状態になると、クラスタ全体が2〜3倍
遅くなりました（prose 34 → 65 tok/s、prefill 2.6K → 6.3K tok/s、構造化出力 86 → 165 tok/s）。

復旧には**電源ケーブルを抜いて30秒**（ECリセット）が必要です。再起動では直りません。
上流の文書は「サービスを止めたままにすればNVIDIAのカーブが残る」としていますが、私たちの
4台ではそうなりませんでした。ファンのRPMは「そうなっているはず」ではなく**測って確かめる**
対象だと考えてください。

そこから導いた2つの方針:

1. デーモンを動かし続ける（`deploy/`のユニットは`Restart=always`相当）、そして
2. カーブがstate 1未満を要求できないようにする。デーモンが止まってもしくは固まっても、
   0 RPMの要求が残らないようにする（パッチの`(0.0, 1)`）。

## 使っているカーブ

上流は`(50°C, 3) (55, 5) (60, 8) (65, 10) (70, 12)`を要求し、50 °C未満ではstate 0を要求します。
このパッチは約62 °Cまで冷却要求を下げ、同時にstate 1を下限にします。

| 平滑化後の最高温ゾーン | このカーブ | state | 共通フロア |
|---|---|---|---|
| 52 °C未満 | (0.0, 1) | 1 | 2,700 RPM |
| 52 °C | (52.0, 2) | 2 | 3,600 |
| 57 °C | (57.0, 3) | 3 | 4,500 |
| 62 °C | (62.0, 4) | 4 | 5,400 |
| 66 °C | (66.0, 5) | 5 | 6,300 |
| 70 °C | (70.0, 6) | 6 | 7,200 |
| 73 °C | (73.0, 8) | 8 | 9,000 |
| 76 °C | (76.0, 10) | 10 | 11,250 |
| 78 °C以上 | (78.0, 12) | 12 | 9,000 / 13,500 |

78 °C以上は意図的に上流の最大値です。私たちの警報線がACPI 78 °C / GPU 75 °Cなので、
最後の数度はわざと全開にしています。平滑化とレート制限は上流のまま: `alpha=0.35`、
2秒サンプルあたり最大+2 state、サンプルあたり−1 state、下降時は4 °Cのヒステリシス、
転送失敗3回でstate 12。

stateは**要求値**として読んでください。ファームウェアは自身の要求とこの要求の最大値を採るので、
実測RPMは表の値ではなく上側のエンベロープになります。

## 何が変わったか（実測）

負荷ハーネス: ノードあたり700トークン生成を2並列、6波、4ノード全てで配信、プロンプトは前後で同一。

| 構成 | アイドル | 中負荷 | 速度 |
|---|---|---|---|
| デーモン停止（モジュールのみ） | 0 RPM・SoC 96 °C・GPU 611 MHz固定 | — | 下段より2〜3倍遅い |
| 上流のカーブ | state 10–12・10,935–13,500 RPM | — | 基準 |
| このカーブ・第1段（+5 °Cシフト） | state 3・4,500–5,670 RPM | ACPI 63–69 °C・state 3–5・4,450–6,300 RPM | 変化なし |
| このカーブ・現行（+7 °Cシフト・下限1） | state 2・3,600–4,185 RPM・ACPI 50–53 °C | ACPI 65–73 °C・state 5–6・5,400–7,200 RPM | 変化なし（700 tok 10.7–10.9秒、400 tok 5.6秒） |

正直な損得: アイドルRPMは約20%下がり（4,500 → 3,600）、中負荷の温度は約4 °C上がり、
stateは1段上がりました。同じ仕事を同じシリコンで裁くので、平衡点が「温度を上げて回転を
下げる」側へ移っただけです。**実際の負荷では音はほとんど変わりません。** Sparkの音を
本気で下げたいなら、カーブよりも配置（別室・戸棚・吸排気の余裕）を直すべきです。

## ファームウェア: 2026年10月のセットは入れない

ファン制御は、10月のセットで取り除かれたファームウェアの経路に依存しています。
9月のセットで測った値と、NVIDIAが提示した値:

| 部品 | 2026年9月（ファン制御が動く） | 2026年10月（ファン制御が壊れる） |
|---|---|---|
| EC | 3.5.8（`0x03000508`） | 3.13.7（`0x03000d07`） |
| SoC | 2.155.11（`0x02009b0b`） | 2.158.15（`0x02009e0f`） |
| USB-C PD | 5.22（`0x00000516`） | 5.25（`0x00000519`） |

10月のセットで観測したこと: フロアの書き込み（cmd 3/5）が`0xff`で拒否され、読みは`0xffff`を
返し、オーバーライドのコードは消え、ファン範囲は1,260–9,000 / 1,890–13,500ではなく
975–4,350 RPMに制限されました。新しいSoCと古いECの組み合わせも動きません（リレーのタイムアウト、
tach 0/0）。つまり簡単なダウングレード経路はありません。詳細と、私たちが使った凍結手順:
`docs/firmware.md`。

## 導入

```sh
# 1. モジュールの自動ロード（これがロードされている間だけ cooling device が存在する）
sudo install -m 644 deploy/dgx_ec_fan_control.conf /etc/modules-load.d/dgx_ec_fan_control.conf
sudo modprobe dgx_ec_fan_control

# 2. ユーザーランド制御器: 上流のチェックアウト＋このパッチ
git clone https://github.com/christopherowen/dgx-spark-fan-control
cd dgx-spark-fan-control && patch -p1 < /path/to/0001-performance-curve.patch
sudo install -m 755 userspace/dgx_fan_control.py /usr/local/sbin/dgx-fan-control

# 3. デーモン
sudo install -m 644 deploy/dgx-fan-daemon.service /etc/systemd/system/dgx-fan-daemon.service
#    上流のベンチは "dgx-fan-control.service" を停止/開始する:
#    同じデーモンに解決するよう別名を足す
sudo ln -sf /etc/systemd/system/dgx-fan-daemon.service /etc/systemd/system/dgx-fan-control.service
sudo systemctl daemon-reload
sudo systemctl enable --now dgx-fan-daemon.service

# 4. 確認（ここを飛ばす人が多い）
scripts/fan-snapshot.sh          # state・最高温ゾーン・2つのファンRPM・GPUクロック/電力
```

別名を省くのは自己責任で。ユニット名が解決しないと、上流のベンチは
`cannot restore fan control`で中止し、測定結果が1つも出ません。

## 監視

- `scripts/fan-snapshot.sh` — 読み取り専用の1回実行: 要求state、最高温ゾーン、
  `fan1_input`/`fan2_input`、GPU温度/クロック/電力。cronから回しても安全。
- `scripts/thermal-watch.sh` — ACPI ≥ 78 °C、GPU ≥ 75 °C、または**現行**のファンstateが0で
  警報。設定はファイル冒頭の環境変数（ホスト一覧・sshユーザー・警報ファイル）。
  判定は`dmesg`の`baseline fan1=`行ではなく、動いているstateで行ってください。私たちの1台は
  ファンが正常に回っていてもbaselineが0と記録され、誤報の原因になりました。

## 互換性の注意

- 私たちのノードではkernel `7.0.0-1019-nvidia-64k`（64 KBページ）とEC 3.5.8で動作。
  上流は`6.17.0-1029-nvidia`と同一ECで検証済み。それ以外のカーネルと、10月のファームウェアは
  ここでは未検証です。
- 4ノードで1つのtensor-parallelモデルを配信して測定しました。1台だけのアイドルでは温度の
  振る舞いは同じですが、熱くなるSoCが1つだけなのでRPMの平衡点は変わります。
- このカーブは**加算的なフロア**です。ファームウェアが求める以上に静かにはできませんし、
  ファームウェアの上限を超えることもできません。センサーが冷えているのにファンが全開に
  張り付くなら、それはこのパッチではなくファームウェア自身の要求です。
